# Project scaffold

This skill turns approved stack decisions into a running skeleton. Each component the approved architecture
names (an app, a public site, a worker) is generated by its stack's official starter, with every choice passed as
a flag, at a version checked in this session, and committed untouched before anyone changes it. What the
components are, and which stack each one uses, was settled in `project-inception`; agent plugins come after, in
`stack-bootstrap`. The failure it prevents: a skeleton built by hand from memory (missing auth hardening, a test
setup that runs nothing, a stale framework major), or a project that gets an admin panel, a marketing site and a
Go worker it never asked for, because "a project usually has those".

## Applies when / does not apply

- Applies: "scaffold the app", "set up the project", "create the Laravel app", "start the Nuxt site", a plan step
  that creates a new component, a new component added to an existing repository (a worker, a site).
- Does not apply: writing the docs and settling the stack (`project-inception`), choosing a framework, enabling
  agent plugins (`stack-bootstrap`), adding a dependency to an existing component (`build-vs-buy`), upgrading a
  framework in place.

## Rules

- [invariant] Scaffold only on request or when an approved plan schedules it, and only the components the
  approved docs name. No component "for later": a project whose architecture names one Laravel app gets one
  Laravel app, not a public site, an admin panel, a Go worker or a monorepo layout around it. A component that
  seems missing is an open question for the owner, not a scaffold. Why: every generated component is code someone
  maintains, patches and deploys; a component nobody asked for is cost without a decision. Test: the approved
  architecture names only a Laravel app; asked to "set up the whole project", the agent creates only the Laravel
  app and asks about anything else. Source: none; design judgment, consistent with `project-inception` (the
  scaffold is the stack decision).
- [invariant] Without approved stack decisions there is no scaffold. If `docs/plans/*-inception.md` is not
  Approved, or the component's stack is still an open decision, stop and point to `project-inception`. Test: a
  repository whose inception record says Draft; asked to scaffold, the agent reports the open gate and creates no
  files. Source: none; design judgment, consistent with `project-inception` (approval gate).
- [invariant] Write the component list first. Before the first command, fill the Scaffold table in
  `docs/PROJECT-FACTS.md` (component, directory, starter, version, flags) with one row per approved component, and
  show it. `scripts/check_scaffold.py` compares the repository against this table. Test: the transcript shows the
  table before the first installer command. Source: none; design judgment.
- [invariant] Use the stack's official starter, and pass every choice as a flag. Run the installer
  non-interactively (`--no-interaction`, `-n`, `< /dev/null`); never answer an interactive prompt by guessing. The
  starter's options and the installer's own version are looked up in this session (`--help`, the registry, the
  docs), because an outdated installer lacks options without saying so. Never hand-build what a starter
  generates: auth screens, layouts, build config, test setup, lint config. Why: the starter carries the
  framework team's current defaults and security fixes; a hand-built copy carries the model's memory of an older
  release. Test: with an installer older than the registry's latest, the agent updates it or runs the current one
  in an isolated location before scaffolding. Source: https://laravel.com/docs/starter-kits, verified 2026-11-04.
- [invariant] The first commit is the untouched starter output with its lockfiles, message
  `chore: scaffold [component] from [starter] [version]`, and the starter's own tests and build pass before any
  change of yours. A red starter is an environment problem (runtime version, missing extension, missing service);
  fix the environment, not the generated code. Why: it separates generated code from authored code in every later
  review and gives a known-good point to return to. Test: the second commit is the first one that changes
  generated files. Source: none; design judgment, consistent with `commit-hygiene`.
- [invariant] Remove no starter feature silently. Dropping registration, two-factor auth, email verification,
  passkeys, the test suite or the lint setup is an owner decision recorded as an ADR. Adding packages during the
  scaffold beyond the approved ones is the same. Test: asked to "keep it minimal", the agent lists the starter
  features it would remove as an open decision instead of deleting them. Source: none; design judgment.
- [invariant] After the alignment commits, audit the skeleton for starter leftovers against the approved specs:
  for each generated table, migration, config file, driver default, seeder, route and page, ask whether the
  approved app uses it. List the ones it does not use for the owner with a proposal per item (keep, remove, or
  switch the driver), and keep nothing silently and delete nothing silently. Agreed removals land in their own
  commits, each with its check, and a guard test then pins the set of tables the app is allowed to have, so a
  leftover cannot come back with the next package. Why: a starter carries the framework's general defaults (a
  database queue, a database cache, a demo user), and every unused one is a table, a config and an attack
  surface someone maintains without a decision. Test: a Laravel skeleton for an app whose approved runtime spec
  chose Redis for queue and cache; the report lists the `jobs`, `job_batches`, `cache` and `cache_locks`
  tables, the `database` driver defaults and the seeded demo user as leftovers with a proposal each, and no file
  was removed before the owner answered (eval `adversarial-scaffold-leftovers`). Source: none; design judgment,
  consistent with the rule above on starter features.
- [default] Favorites per stack are in `references/starters.md`. An owner profile, `AGENTS.md` or an ADR that
  names other favorites wins over the table. Trade-off: the favorite fits the common case, not every case.
  Deviate only with an ADR that names this trade-off. Source: `references/starters.md`, verified 2026-11-04.
- [default] After the untouched commit, align the skeleton with the approved specs in small commits, each with
  its check: the production database engine in `.env.example`, the runtime pin (for PHP `config.platform.php` in
  `composer.json`), a test lane on the production database engine, the locales the product needs. Trade-off: a
  few extra commits. Deviate only with an ADR that names this trade-off. Source: none; design judgment.

## Procedure

### Fast path

One approved component, one favorite starter: confirm the gate, fill one table row, run the starter command from
`references/starters.md` with its flags, run its tests, commit untouched, run `check_scaffold.py`, report.

1. Gate: read the inception record and the architecture spec. Approved and the component's stack settled? If
   not, stop and name the open decision.
2. List: one row per approved component in the Scaffold table of `docs/PROJECT-FACTS.md`. Show it.
3. Look up: for each row, the starter's current version (registry), the installer's version and its `--help`.
   Note both with the command that showed them.
4. Generate: one component at a time, non-interactively, into its directory from the table.
5. Prove: install dependencies, run the starter's tests and build, read the counts. Green, then the untouched
   commit. Red: fix the environment and run again (`goal-focus` attempt cap).
6. Align: the default above, one commit and one check per change.
7. Audit leftovers: list every generated table, driver default, config, seeder, route and page the approved
   specs do not use, with a proposal each (`references/starters.md` lists the usual ones per starter). Ask the
   owner; remove only what was agreed, one commit each, then add the guard test on the allowed tables.
8. Check: `python3 scripts/check_scaffold.py [repo]`. Then hand over to `stack-bootstrap`.
9. Report: components created with starter and version, test and build counts, the commits, what was not created
   and why, the leftover list with the owner's decision per item, open questions.

## Traps

- An installer from an old global install offers fewer kits and flags and still exits 0. Compare its version with
  the registry first.
- A starter's test suite that runs on SQLite in memory passes while production runs PostgreSQL. Green starter
  tests prove the skeleton works, not that the production database lane exists.
- An installer that initialises no git repository by default; the untouched commit has to be made explicitly.
- Answering an installer prompt in a pipe with `yes` picks whatever the first option is.
- Removing a starter feature in a framework with typed routes breaks the build where the frontend still
  references the removed routes.
- "Like the last project" is not a stack decision; read the approved docs.
- A leftover table that a package still uses: Laravel's failed-job store writes to `failed_jobs` by default even
  when the queue runs on Redis. Check the config that reads a table before proposing its removal.

## Done when

- Every row of the Scaffold table exists as a directory generated by its starter, and nothing else was generated.
- The installer and starter versions were looked up in this session and are written in the table.
- The first commit per component is untouched starter output; its tests and build ran green, with counts quoted.
- The leftover audit is in the report with the owner's decision per item; agreed removals are committed and a
  guard test pins the allowed tables.
- `check_scaffold.py` exits 0.
