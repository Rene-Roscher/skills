# Pinning and updates

## Choosing the mechanism

- Workflow lockfile: `.github/workflows/actions.lock`, generated by the `gh actions-lock` CLI extension and never
  edited by hand. It pins a commit SHA for every action the workflows depend on, transitive dependencies included.
  Dependencies of a called reusable workflow are covered by the lockfile of the repository that defines it.
  For onboarded workflows, SHA pins inside the workflow files are no longer needed, and the lockfile satisfies the
  "Require actions to be pinned to a full-length commit SHA" policy.
- Inline SHA pins: `uses: owner/repo@[full commit SHA] # v4.4.0`. Use them where the lockfile is not adopted or not
  available on your GitHub product.
- Both satisfy the pinning rule. Don't mix them inside one workflow without saying which one is authoritative.

What the lockfile does not cover, per its docs (checked 2026-10-31):

- Reusable workflow calls (`jobs.<job_id>.uses`). Pin them by full SHA.
- Input parameters, secrets and the runner image.
- The docs are silent on `docker://` step images, local actions (`./.github/actions/x`) and nested `uses:` inside
  composite actions. Pin images by digest, and treat coverage of the others as unverified until the docs say so.

Enforcement: `gh actions-lock --verify` as a required pull-request check fails on a stale lockfile. Organization
and repository policies can require SHA pins or require the lockfile.

## Resolving a SHA

1. Take the tag from the action's own repository: `git ls-remote --tags https://github.com/OWNER/REPO 'v4.4.0*'`.
   An annotated tag lists two lines; the one ending in `^{}` is the commit.
2. Confirm that the commit belongs to that repository and not only to a fork in its network:
   `gh api repos/OWNER/REPO/commits/SHA` succeeds for both, so also check that a branch or tag of OWNER/REPO
   contains it. zizmor `impostor-commit` automates this.
3. Write the SHA with the exact version as the trailing comment. zizmor `ref-version-mismatch` fails when the
   comment and the SHA disagree.

Never take a SHA from a blog post, a search result or another repository's workflow.

## Updaters

Dependabot and Renovate are equally valid. Pick one per repository, not both.

- Dependabot: ecosystem `github-actions`, directory `/`. Dependabot then searches `/.github/workflows` and a root
  `action.yml` or `action.yaml`. Composite actions elsewhere need their own `directories` entry.
- Dependabot cooldown: version updates get a 3-day cooldown even when `cooldown` is not set. Security updates have
  no cooldown. For `github-actions` and `docker` only `default-days` applies; the semver-specific day settings are
  not supported for those ecosystems.
- With the lockfile, Dependabot updates the lockfile entry in the same pull request (GA changelog,
  https://github.blog/changelog/2026-10-28-github-actions-workflow-lockfiles-are-generally-available/).
- Renovate: preset `helpers:pinGitHubActionDigests`. Renovate's docs don't mention the lockfile (checked
  2026-10-31); don't assume it regenerates `actions.lock`.
- Whether Dependabot rewrites the trailing version comment together with the SHA is not stated on the docs pages
  read. Check it on the first update pull request: `ref-version-mismatch` must still pass.

## Review of updater pull requests

- The full CI runs on them, including the workflow lint.
- No auto-merge into workflows that hold write scopes, `id-token: write` or deploy secrets.
- When a pin moves for a security reason, the commit message names the advisory and links it.
- Grouping keeps the pull request count manageable. One group per ecosystem is a common choice.
