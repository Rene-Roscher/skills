# GitHub Actions hardening

This skill decides where a workflow's code comes from, what its token may do, how it gets cloud credentials, and
which gates a release must pass, so that a moved tag, a crafted branch name or a fork pull request cannot run code
with release rights. Syntax stays in GitHub's workflow reference and zizmor's audit list. This skill keeps the
decisions, the check that proves each one, and the traps. It prevents a pipeline that publishes, signs or deploys
from a state nobody tested or reviewed.

## Applies when / does not apply

- Applies: creating, editing or reviewing `.github/workflows/*.yml`, `action.yml`, `.github/dependabot.yml` or a
  Renovate config; adding a release, publish or deploy job; giving a workflow cloud credentials or secrets;
  choosing runners; fixing zizmor or actionlint findings.
- Does not apply: GitLab CI, Jenkins and other CI systems; what goes into an image (`container-images`); changing
  repository or organization settings yourself. A settings change has effects outside the working tree and goes
  through `safe-actions`. This skill produces the checklist and a read-only audit.

## Rules

Ordered by blast radius. Each rule names the check that proves it, so the target repository enforces it in CI.

- [invariant] **Immutable action references.** Where the repository has adopted the workflow lockfile
  (`.github/workflows/actions.lock`, generated by the `gh actions-lock` extension, never edited by hand), the
  lockfile pins the actions; otherwise every `uses:` carries the full 40-character commit SHA from the action's own
  repository with the version as a trailing comment. Either satisfies this rule. Reusable workflow calls
  (`jobs.<job_id>.uses`) take a SHA in both cases, because the lockfile does not pin them, and `docker://` step
  images, `container:` and `services:` images take a digest. Why: whoever controls an action repository can move a
  tag, and the moved tag then runs with the job's token, secrets and OIDC identity; in a 2025 compromise attackers
  retargeted version tags of a widely used action to a commit that printed secrets into build logs
  (https://github.com/advisories/GHSA-mrrh-fwg8-r2c3). Test: zizmor `unpinned-uses` (since v1.20.0 its default
  policy requires hash pins for all actions, `actions/*` included), `unpinned-images`, `impostor-commit` and
  `ref-version-mismatch` report nothing; with the lockfile, `gh actions-lock --verify` runs as a required check
  and fails on a stale lockfile; for every inline pin, `gh api repos/[owner]/[repo]/commits/[tag] --jq .sha` prints
  the pinned SHA, which fails for the SHA of an annotated tag object. Source:
  https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles,
  https://docs.github.com/en/actions/reference/security/secure-use, https://docs.zizmor.sh/audits/ (verified 2026-10).
- [invariant] **Pins have an updater, and its pull requests are reviewed.** Enable Dependabot's `github-actions`
  ecosystem or Renovate with `helpers:pinGitHubActionDigests`; both are equally valid. Set the cooldown on version
  updates explicitly to at least 7 days (Dependabot `cooldown.default-days: 7`, Renovate `minimumReleaseAge`), and
  never auto-merge updater pull requests into workflows that publish or deploy. Why: a pin nobody updates keeps
  known-vulnerable code, and a cooldown keeps a freshly published malicious release out of routine update pull
  requests. Dependabot's implicit default is 3 days, below zizmor's default threshold of 7, so a config without an
  explicit cooldown fails the audit on its first run; for `github-actions` and `docker` only `default-days` is
  supported. Test: the updater covers directory `/` for actions (Dependabot then reads
  `/.github/workflows` and a root `action.yml`); zizmor `dependabot-cooldown`, `dependabot-execution` and
  `known-vulnerable-actions` report nothing; after the first update pull request `ref-version-mismatch` still
  passes, which shows the version comment moved with the SHA. Source:
  https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference,
  https://docs.renovatebot.com/presets-helpers/ (verified 2026-10), https://docs.zizmor.sh/audits/
  (`dependabot-cooldown` default threshold 7 days), https://docs.renovatebot.com/configuration-options/
  (`minimumReleaseAge`) (verified 2026-11-05).
- [invariant] **Least-privilege token, granted per job.** Start every workflow with `permissions: {}` (or
  `contents: read`) and grant write scopes only on the job that uses them, each with a comment saying why. Never
  put a write scope at workflow level in a workflow triggered by `pull_request`. Why: every step and action in a
  job can use the token, and pull requests from branches of the same repository are not reduced to read-only the
  way fork pull requests are. Test: zizmor `excessive-permissions` and `undocumented-permissions` report nothing;
  the workflow checker fails a workflow without a top-level `permissions` key, or with a top-level write scope next
  to a `pull_request` trigger. Source: https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax
  (unspecified scopes become `none`) (verified 2026-10).
- [invariant] **No untrusted data in `${{ }}` inside a shell.** Event data, `github.head_ref`, `github.ref_name`,
  `inputs.*`, step outputs derived from them and artifact contents reach `run:` and `actions/github-script` only
  through `env:`, used as quoted shell variables (`"$PR_TITLE"`). Never write such values to `GITHUB_ENV` or
  `GITHUB_PATH`. Why: expressions expand as text before the shell parses the line, so a crafted title or ref name
  becomes code that runs with the job's secrets. Test: `git check-ref-format 'refs/tags/v1$(id)'` exits 0 (git
  2.43.0), so even a tag name can carry a command substitution; zizmor `template-injection` and `github-env` report
  nothing, and the checker finds no `${{` inside `run:` outside its allowlist. Source:
  https://docs.github.com/en/actions/reference/security/secure-use (intermediate environment variable) (verified 2026-10).
- [invariant] **Privileged triggers never execute pull-request code.** `pull_request_target`, `workflow_run` and
  `issue_comment` run with the base repository's token and secrets. In those workflows, checked-out pull-request
  code and downloaded artifacts are data to inspect, never to build, install, test or run. Execute the change under
  `pull_request`, and let a separate privileged workflow consume validated data. Bot checks read
  `github.event.pull_request.user.login`, not `github.actor`. Why: a privileged trigger plus a checkout of the head
  plus a build step hands secrets and a write token to any fork. Test: zizmor `dangerous-triggers`,
  `bot-conditions` and `cache-poisoning` report nothing; the checker fails a privileged-trigger workflow that checks
  out a pull-request ref and then runs a step outside its allowlist. Source:
  https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target (verified 2026-10).
- [invariant] **Release, publish and deploy wait for the gates on the same commit.** Every job that pushes an
  artifact, signs or deploys has a `needs:` chain to the test jobs in the same run, or calls the test workflow with
  `workflow_call` and needs that job. A test workflow running in parallel does not count, and tag releases re-run or
  call the gates instead of trusting that main was green. Why: a publish job without `needs:` pushes version and
  `latest` tags while the sibling test job is red, and an image-update automation can then roll the untested image
  out unattended. Test: the checker fails when a job with a write scope, `id-token: write` or `environment:` does
  not transitively need a job from the gate list; the branch ruleset lists the gate jobs as required checks.
  Source: https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax (`jobs.<job_id>.needs`)
  (verified 2026-10).
- [invariant] **Gates cannot pass by accident.** No `|| true`, `set +e` or `continue-on-error: true` on a gate
  step. Set `shell: bash` (or `defaults.run.shell: bash`), which runs with `-eo pipefail`; the implicit default is
  `bash -e` without pipefail. Uploads set `if-no-files-found: error`. Filters, globs and loops assert that they
  matched something, and a missing tool fails the job. Independent linters run as separate jobs or steps with
  `if: ${{ !cancelled() }}`, so the first red one does not hide the next. Why: a gate that cannot fail reports
  green on broken code. Test: `go test -run DoesNotExist ./...` prints `[no tests to run]` and exits 0 (go 1.27.3);
  each guard ships a seeded-bad fixture that must turn it red, and the checker flags the three escape hatches
  without an `# allow:` reason. Source: https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax
  (`defaults.run.shell`) (verified 2026-10).
- [invariant] **Privileged jobs run only pinned, verified tools.** In a job holding a write scope,
  `id-token: write` or secrets, install third-party binaries from a versioned release URL and check them with
  `sha256sum -c` against a checksum stored next to the version, or use a SHA-pinned action with an explicit tool
  version. No download piped into a shell, no `@latest`, no `version: latest`. Read-only jobs pin versions too.
  Why: anything that runs in a job with `id-token: write` can exchange the token for a signing certificate on the
  release identity. Test: zizmor `unpinned-tools` and `adhoc-packages` report nothing; the checker finds no
  `@latest`, `version: latest` or download-to-shell pipe. Source: https://docs.zizmor.sh/audits/ (verified 2026-10).
- [invariant] **Cloud and registry access uses OIDC with narrow trust conditions.** Request `id-token: write` only
  on the job that exchanges it. Push to registries with `GITHUB_TOKEN` or OIDC, not personal access tokens, and use
  trusted publishing where the package registry offers it. The cloud-side trust policy pins the subject to the
  repository plus an environment or ref, never only the owner. Why: without a condition, other repositories can
  request access tokens. Test: zizmor `use-trusted-publishing` and `overprovisioned-secrets` report nothing; an
  infrastructure test asserts that the trust policy's `sub` condition names the repository and an environment or
  ref. Source: https://docs.github.com/en/actions/reference/security/oidc (verified 2026-10).
- [invariant] **Self-hosted runners keep trust levels apart.** No self-hosted runners on public repositories. Jobs
  with `id-token: write`, write scopes or production secrets never run on persistent runners that also run
  pull-request or other untrusted jobs; they use ephemeral or just-in-time runners in a group reserved for release
  work. No Docker socket, host network or shared tool cache across trust levels, and a
  `runs-on: ${{ vars.X || 'ubuntu-latest' }}` switch must not move signing jobs onto shared runners. Why: GitHub
  states that a self-hosted runner can be persistently compromised by untrusted code and cannot be guaranteed to run
  only one job. Test: the checker fails a job with `id-token: write` or a write scope whose runner label is not on
  the release allowlist; a read-only `gh api` audit lists runner groups and their repository access. Source:
  https://docs.github.com/en/actions/reference/security/secure-use,
  https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access (verified 2026-10).
- [default] **Every job sets `timeout-minutes`**, about two to three times its observed p95. The default is 360
  minutes, and a hung job blocks a runner and its concurrency group. Trade-off: a slow but healthy run gets cut and
  needs a re-run. Deviate only with an ADR that names this trade-off. Source:
  https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax (verified 2026-10).
- [default] **Concurrency cancels CI, never releases.** CI groups by workflow and ref with
  `cancel-in-progress: true`. Release and deploy workflows use `cancel-in-progress: false` with `queue: max`.
  Cancelling a running release can stop it between push and sign, which leaves pushed but unsigned artifacts. The
  default `queue: single` cancels the pending run when another one queues, so a release is dropped without notice.
  Trade-off: queued releases run one after another. Deviate only with an ADR that names this trade-off. Source: https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency
  (`queue: max` holds up to 100 pending runs and cannot be combined with `cancel-in-progress: true`) (verified 2026-10).
- [default] **Credentials stay where they are needed.** `actions/checkout` with `persist-credentials: false`
  unless the job pushes with git; named secrets forwarded to reusable workflows instead of `secrets: inherit`;
  production deploy secrets in an environment with required reviewers and branch or tag rules; no JSON secrets
  whose fields escape log redaction. Trade-off: more explicit wiring in every workflow. Deviate only with an ADR
  that names this trade-off. Test: zizmor `artipacked`, `secrets-inherit`, `secrets-outside-env` (auditor persona)
  and `unredacted-secrets` report nothing. Source: https://docs.zizmor.sh/audits/ (verified 2026-10).
- [default] **Jobs that sign or publish do not read the Actions cache.** Turn off implicit caching in setup actions
  (`actions/setup-node` v7 caches npm automatically when `package.json` names npm as its package manager;
  `actions/setup-go` v7 caches by default) and use no `type=gha` build cache there. Trade-off: slower release
  builds. Deviate only with an ADR that names this trade-off. Test: zizmor `cache-poisoning` reports nothing.
  Source: https://docs.zizmor.sh/audits/ ("release workflows should not read from the GitHub Actions cache"),
  https://github.com/actions/setup-node, https://github.com/actions/setup-go (verified 2026-10).
- [default] **Keyless signing triggers only from protected refs.** Release workflows that sign keyless run on
  pushes of `v*` tags protected by a tag ruleset, or on a protected default branch, and carry no
  `workflow_dispatch`. Verifiers pin the identity with an anchored `--certificate-identity-regexp` and
  `--certificate-oidc-issuer https://token.actions.githubusercontent.com`. Why: the signing identity comes from the
  triggering ref, so a dispatch from main signs as `refs/heads/main`, and widening the verifier to accept that lets
  anyone who can push to main mint release certificates. Trade-off: no manual release re-run from the UI; push a
  new tag instead. Deviate only with an ADR that names this trade-off. Source:
  https://github.com/sigstore/cosign/blob/v3.1.4/doc/cosign_verify.md (verified 2026-10).
- [default] **Shared pipelines are reusable workflows or composite actions, not copies.** Callers reference them
  by commit SHA. Copies drift until a test gate or runner guard exists in only some of them. Trade-off: a change
  to the shared workflow needs a SHA bump in every caller. Deviate only with an ADR that names this trade-off.
  Source: https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax (`jobs.<job_id>.uses`)
  (verified 2026-10).
- [default] **Workflow linting blocks merges.** actionlint and zizmor run at pinned versions on every pull request
  that touches `.github/**` or `action.y*ml`, and findings fail the check. Fix findings; an inline
  `# zizmor: ignore[rule]` carries a trailing reason. With `--format=sarif` zizmor does not use its finding exit
  codes, so a blocking gate uses plain or `github` output, or a required code-scanning check. Trade-off: pedantic
  findings block a merge until fixed or suppressed with a reason. Deviate only with an ADR that names this
  trade-off. Source: https://docs.zizmor.sh/usage/, https://github.com/rhysd/actionlint (verified 2026-10).
- [default] **A new or changed workflow is rehearsed before its first push.** Run zizmor and actionlint locally at
  the pinned versions, then walk the job graph: for every job, list what it consumes (built frontend assets and
  their manifest, generated code, a service container, an env value, an artifact) and name the step or the
  `needs:` job that produces it in a fresh checkout. Run each job's commands once in a clean clone
  (`git clone [repo] [tmp dir]`), not in the working copy, because the working copy holds build output that a
  runner never has, for example a test job that renders views and needs the asset manifest. Trade-off: minutes of
  local work before each workflow change. Deviate only with an ADR that names this trade-off. Proof: the push
  message or pull request names the zizmor and actionlint versions and their clean result, and the first run is
  green without a follow-up "fix CI" commit. Source: https://docs.zizmor.sh/usage/,
  https://github.com/rhysd/actionlint (verified 2026-11-05).
- [default] **Preflight guards run before anything is pushed.** The job asserts required non-secret variables
  (`: "${VAR:?set VAR in repository variables}"`), required tools on the runner and consistency of coupled flags,
  with `::error::` messages that name the fix. Trade-off: the guard list needs upkeep when configuration changes.
  Deviate only with an ADR that names this trade-off. Test: run the job with the variable unset; it fails before
  the first push step.
- [default] **Workflow changes have a designated reviewer.** CODEOWNERS covers `/.github/`, a ruleset requires
  code-owner review, and a tag ruleset protects `v*`. Trade-off: one more required reviewer on workflow changes.
  Deviate only with an ADR that names this trade-off. Source:
  https://docs.github.com/en/actions/reference/security/secure-use (verified 2026-10).
- [default] **Settings back the files.** Default `GITHUB_TOKEN` permissions read-only, allowed actions
  restricted, the SHA-pinning or lockfile policy on, and an Actions event policy decided for public repositories.
  The agent hands over a checklist and a read-only audit and changes no setting itself. Trade-off: a policy can
  block a workflow that a team member still relies on. Deviate only with an ADR that names this trade-off.
  Source: https://docs.github.com/en/actions/how-tos/administer/enforce-workflow-lockfiles (verified 2026-10).

## Procedure

1. Gate: inventory every workflow, `action.yml` and updater config. List triggers, top-level and per-job
   permissions, jobs with write scopes, `id-token: write`, secrets or `environment:`, runner labels, and every
   `uses:` and image reference.
2. Run zizmor and actionlint at pinned versions if they are available, and record the findings. If they are not
   available, say so and review by hand against the rules.
3. Fix in rule order: references, updater, permissions, injection, triggers, release gating, gate integrity,
   tools, OIDC, runners. Then the defaults.
4. Resolve every SHA from the action's own repository and confirm the version comment matches it. Pin the commit:
   for an annotated tag, `git ls-remote --tags` prints the tag object first and the commit on the line ending in
   `^{}`; `gh api repos/[owner]/[repo]/commits/[tag] --jq .sha` prints the commit directly. Never copy a SHA from
   a search result or a fork.
5. Before stating what a recent platform feature covers (the lockfile, execution protections, event policies),
   check the current GitHub docs, following `evidence-before-claims`. Mark anything the docs don't state as
   unverified.
6. Add the guard artifacts to the target repository and prove each one against its seeded-bad fixture.
7. Before the first push: the rehearsal above (local zizmor and actionlint, the job graph, the jobs' commands in
   a clean clone), and for an updater config an explicit cooldown of at least 7 days.
8. Write the settings checklist and run only the read-only audit. Hand any settings change to an administrator,
   or run it through `safe-actions` with approval.
9. After the push, read the run for the pushed commit, not the newest run:
   `gh run list --commit "$(git rev-parse HEAD)" --workflow [file] --json databaseId,headSha,status,conclusion`,
   then `gh run watch [id] --exit-status`. Updater pull requests, scheduled runs and the previous push all produce
   runs that can be newer or still running.
10. Report per rule: the check that ran and its result, and what was not run. Follow `verify-before-done`: a green
   lint is not a working release.

## Traps

- The lockfile does not pin reusable workflow calls, and its docs don't say whether it covers `docker://` step
  images, local actions or nested `uses:` in composite actions. Pin those by SHA or digest regardless. zizmor's docs
  don't mention the lockfile (checked 2026-10-31), so check how `unpinned-uses` reports onboarded workflows before
  you treat its silence as proof.
- `permissions:` accepts `read-all`, `write-all`, `{}` or a map of scopes set to `read`, `write` or `none`.
  Values such as `minimal` don't exist. Check the workflow syntax reference before writing a value you have not
  seen there.
- `go test -run Name` and similar filters exit 0 when they match nothing, so renaming a test can leave a required
  job green with zero tests. Assert a minimum test count.
- Since 2025-12-08 the `pull_request_target` workflow file and its default checkout come from the default branch
  (https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/).
  GitHub also adds a default rule that disables `pull_request_target` in public repositories without an applicable
  event policy, enforced from 2026-12-02 for affected repositories
  (https://github.blog/changelog/2026-09-17-workflow-execution-protections-in-github-actions-generally-available/).
  A working coverage-comment workflow on a public repository can stop on that date.
- `git ls-remote --tags --refs` hides the peeled `^{}` lines, and `head -1` on the unfiltered output picks the
  tag object. For an annotated tag that SHA is not a commit: `gh api repos/[owner]/[repo]/commits/[tag-object SHA]`
  answers 422 "No commit found" (reproduced 2026-11-05 with `aquasecurity/trivy-action` v0.36.0, git 2.43.0).
- "The latest run" is not the run of your commit. `gh run list --limit 1` or `gh run watch` without an ID can pick a
  Dependabot run, a scheduled run or the previous push, and a green result then describes code you did not push.
  Select by `--commit` and compare `headSha`.
- A test job that passes on the developer machine can fail on the runner because the working copy holds generated
  files (an asset manifest, generated routes or types, a cached config) that a fresh checkout lacks.
- Moving a tag-triggered release to `workflow_dispatch` "to re-run it" changes the signing identity, and the
  project's own verifier then rejects it. Widening the verifier is the wrong fix.

## Done when

- zizmor and actionlint, at pinned versions, report no findings, or each suppression carries a reason; for a new
  or changed workflow they ran locally before the first push.
- Every inline pin is a commit SHA: `gh api .../commits/[tag] --jq .sha` matches it.
- The updater cooldown is set explicitly to 7 days or more.
- The first run of the pushed commit, selected by its head SHA, is green, or its failure is reported.
- The workflow checker fails on its seeded-bad fixture and passes on the repository.
- Every job with a write scope, `id-token: write` or `environment:` transitively needs the gate jobs, and the
  gate jobs are required checks.
- The updater covers the actions ecosystem, and its pull requests are not auto-merged into release workflows.
- The settings checklist and the read-only audit output are handed over, and no setting was changed without
  approval.
- Every claim about a recent platform feature has a docs link or is marked unverified.
